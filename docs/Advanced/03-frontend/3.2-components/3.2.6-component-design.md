# 3.2.6 Khối lego bao nhiêu là vừa——Thiết kế component

### Tóm tắt một câu

Component tốt như khối lego—đủ nhỏ để linh hoạt kết hợp, đủ đầy đủ để sử dụng độc lập.

### Giá trị cốt lõi

Thiết kế component quyết định khả năng maintain của code. Component thiết kế không tốt sẽ hoặc quá to khó sửa đổi, hoặc quá phân mảnh khó hiểu.

### Nguyên tắc Single Responsibility

**Một component chỉ nên có một lý do để thay đổi.**

// Sai: Một component gánh quá nhiều trách nhiệm

### Presentational components vs Container components

| Loại | Trách nhiệm | Đặc điểm |
|------|------|------|
| **Presentational component** | Render UI | Nhận Props, không có logic state |
| **Container component** | Quản lý data | Xử lý state, effects, data fetching |

```tsx
// Presentational component: Chỉ chịu trách nhiệm render
interface UserCardProps {
  name: string
  avatar: string
  email: string
}

function UserCard({ name, avatar, email }: UserCardProps) {
  return (
    <div className="card">
      <img src={avatar} alt={name} />
      <h3>{name}</h3>
      <p>{email}</p>
    </div>
  )
}

// Container component: Chịu trách nhiệm data
function UserCardContainer({ userId }: { userId: string }) {
  const { data: user, loading } = useFetch(`/api/users/${userId}`)

  if (loading) return <Skeleton />
  return <UserCard {...user} />
}
```

### Composition pattern

Thông qua `children` và slot để thực hiện composition linh hoạt:

```tsx
// Card component cơ bản
interface CardProps {
  children: React.ReactNode
  header?: React.ReactNode
  footer?: React.ReactNode
}

function Card({ children, header, footer }: CardProps) {
  return (
    <div className="card">
      {header && <div className="card-header">{header}</div>}
      <div className="card-body">{children}</div>
      {footer && <div className="card-footer">{footer}</div>}
    </div>
  )
}

// Sử dụng linh hoạt
<Card
  header={<h2>Thông tin user</h2>}
  footer={<button>Chỉnh sửa</button>}
>
  <p>Tên: Nguyễn Văn A</p>
  <p>Email: nguyen@example.com</p>
</Card>
```

### Compound component pattern

Với UI phức tạp, kết hợp các component liên quan:

```tsx
// Định nghĩa compound component
const Tabs = ({ children, defaultValue }: TabsProps) => {
  const [activeTab, setActiveTab] = useState(defaultValue)
  return (
    <TabsContext.Provider value={{ activeTab, setActiveTab }}>
      {children}
    </TabsContext.Provider>
  )
}

Tabs.List = function TabsList({ children }) {
  return <div className="tabs-list">{children}</div>
}

Tabs.Tab = function Tab({ value, children }) {
  const { activeTab, setActiveTab } = useTabsContext()
  return (
    <button
      className={activeTab === value ? 'active' : ''}
      onClick={() => setActiveTab(value)}
    >
      {children}
    </button>
  )
}

Tabs.Panel = function TabPanel({ value, children }) {
  const { activeTab } = useTabsContext()
  if (activeTab !== value) return null
  return <div>{children}</div>
}

// Sử dụng
<Tabs defaultValue="tab1">
  <Tabs.List>
    <Tabs.Tab value="tab1">Tab 1</Tabs.Tab>
    <Tabs.Tab value="tab2">Tab 2</Tabs.Tab>
  </Tabs.List>
  <Tabs.Panel value="tab1">Nội dung 1</Tabs.Panel>
  <Tabs.Panel value="tab2">Nội dung 2</Tabs.Panel>
</Tabs>
```

### Timing để tách component

**Dấu hiệu cần tách:**
1. Component vượt quá 200 dòng code
2. Có khối UI độc lập rõ ràng
3. Logic có thể được tái sử dụng
4. Cần test riêng một phần
5. Khi nhiều người cùng làm cần giảm conflict

**Trường hợp không cần tách:**
1. Sau khi tách chỉ dùng ở một chỗ
2. Tách dẫn đến việc truyền Props phức tạp hơn
3. Tách xong lại khó hiểu hơn

### Hướng dẫn cộng tác AI

**Ý định cốt lõi**: Để AI giúp bạn phân tích và refactor cấu trúc component.

**Công thức định nghĩa yêu cầu**:
- Mô tả chức năng: Component này hiện tại [đang làm gì]
- Cách tương tác: Trong đó [phần nào] là độc lập
- Hiệu quả kỳ vọng: Hy vọng sau khi tách [đạt được hiệu quả gì]

**Thuật ngữ chính**: Single responsibility, presentational component, container component, compound component, composition pattern

**Chiến lược tương tác**:
1. Cho AI xem component lớn hiện tại
2. Để nó phân tích ranh giới có thể tách
3. Thảo luận ưu nhược điểm phương án tách
4. Từng bước refactor

### Hướng dẫn tránh hố

1. **Đừng tách vì tách**: Tách quá mức tăng chi phí hiểu code
2. **Giữ naming nhất quán**: `UserCard`, `UserCardContainer`, `useUserCard`
3. **Cân nhắc consumer của component**: Thiết kế API phải đúng trực giác
4. **Tránh Props explosion**: Quá 7-8 Props cân nhắc thiết kế lại

### Checklist nghiệm thu

- [ ] Mỗi component có single responsibility rõ ràng
- [ ] Presentation logic và business logic phân tách hợp lý
- [ ] Dùng composition pattern thực hiện tính linh hoạt
- [ ] Tổ chức file rõ ràng hợp lý
