# 3.5.4 Quản lý context: Để AI nhớ những gì bạn đã nói

## Sau khi học tiểu mục này, bạn sẽ nắm vững

- Hiểu "trí nhớ" của AI hoạt động như thế nào
- Nhận biết tín hiệu "tràn" context
- Bốn kỹ thuật quản lý context thực dụng
- Sử dụng cấu hình cấp công cụ để AI "tự động nhớ" quy chuẩn dự án

## "Trí nhớ" của AI hoạt động như thế nào

Trước tiên hãy hiểu một khái niệm then chốt: AI không có "trí nhớ" thực sự.

Mỗi lần bạn đối thoại với AI, AI nhìn thấy là **toàn bộ lịch sử đối thoại**. Giống như bạn đưa một chồng giấy cho một người, bảo họ đọc xong rồi trả lời câu hỏi. Giấy càng nhiều, thông tin họ cần xử lý càng nhiều.

Chồng "giấy" này có một cái tên: **Context Window**.

### Dùng "bàn làm việc" để hiểu

Hãy tưởng tượng context window của AI là một bàn làm việc:

```
┌────────────────────────────────────────────┐
│                 Bàn làm việc của AI          │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐      │
│  │ Vòng 1│ │ Vòng 2│ │ Vòng 3│ │ Vòng 4│ ...  │
│  │đối thoại│ │đối thoại│ │đối thoại│ │đối thoại│      │
│  └──────┘ └──────┘ └──────┘ └──────┘      │
│                                            │
│  Kích thước bàn làm việc có giới hạn (ví dụ 128K tokens)   │
└────────────────────────────────────────────┘
```

**Đặc điểm của bàn làm việc**:
- Kích thước có hạn (mô hình khác nhau thì khác nhau, thường 8K-200K tokens)
- Khi không đủ chỗ, **nội dung sớm nhất sẽ bị "đẩy ra ngoài"**
- Nội dung bị đẩy ra, AI sẽ "quên"

### Kích thước context window của các mô hình khác nhau

| Mô hình | Context Window | Tương đương khoảng |
|-----|-----------|-----------|
| GPT-4o | 128K tokens | Khoảng 300 trang tài liệu |
| Claude 3.5 Sonnet | 200K tokens | Khoảng 500 trang tài liệu |
| DeepSeek | 64K tokens | Khoảng 150 trang tài liệu |
| Mô hình cũ hơn | 4K-8K tokens | Khoảng 10-20 trang tài liệu |

Trông có vẻ lớn? Nhưng trong đối thoại dài, tốc độ tiêu thụ nhanh hơn bạn tưởng.

## Tín hiệu "tràn" context

Khi đối thoại quá dài, nội dung đầu bị đẩy ra khỏi context window, sẽ xuất hiện "tràn".

### Triệu chứng thường gặp

| Triệu chứng | Biểu hiện | Nguyên nhân |
|-----|------|------|
| AI đột nhiên "mất trí nhớ" | Quên tech stack hoặc quy tắc đặt tên đã thỏa thuận trước | Đối thoại đầu bị đẩy ra |
| Bắt đầu "tự mâu thuẫn" | Câu trả lời trước sau không nhất quán | Chỉ nhìn thấy một phần lịch sử |
| Lặp lại câu hỏi bạn đã hỏi | "Cho hỏi bạn dùng framework gì?" (đã nói trước đó rồi) | Phần đối thoại đó không còn trong window |
| Style code đột biến | Trước dùng TypeScript, đột nhiên bắt đầu viết JavaScript | Quên thỏa thuận tech stack |

### Một kịch bản thực tế

```
Vòng 1: Bạn nói "Hãy dùng TypeScript và Tailwind"
Vòng 2: AI viết code bằng TypeScript
Vòng 3: Tiếp tục dùng TypeScript
...
Vòng 15: Bạn bảo AI viết một component mới
Vòng 16: AI đột nhiên cho bạn code JavaScript ← Vấn đề xuất hiện
```

Đây là tràn context. Thỏa thuận vòng 1 đã bị đẩy ra khỏi bàn làm việc.

## Bốn kỹ thuật quản lý context

### Kỹ thuật một: Thông tin then chốt đặt lên đầu

Ở đầu mỗi vòng đối thoại, nhắc lại thỏa thuận then chốt.

```markdown
Tiếp tục dự án danh sách việc cần làm của chúng ta.

Nhắc nhở:
- Tech stack: React + TypeScript + Tailwind
- Quy tắc đặt tên: Component dùng PascalCase, function dùng camelCase
- Tất cả function cần khai báo type

Bây giờ hãy giúp tôi thực hiện [chức năng mới]...
```

**Hiệu quả**: Thông tin then chốt luôn trong "tầm nhìn" của AI.

### Kỹ thuật hai: Tóm tắt định kỳ

Khi đối thoại tiến hành trên 10 vòng, chủ động để AI tóm tắt công việc đã hoàn thành.

```markdown
Chúng ta đã trò chuyện rất nhiều vòng. Hãy tóm tắt trạng thái dự án hiện tại:
1. Chức năng đã hoàn thành
2. Tech stack và thỏa thuận đang sử dụng
3. Chức năng cần hoàn thành

Sau đó chúng ta tiếp tục phát triển.
```

**Hiệu quả**:
- "Nén" thông tin rải rác ở nhiều nơi thành một đoạn tóm tắt
- Tóm tắt ở vị trí mới nhất, sẽ không bị đẩy ra
- Bạn cũng có thể xác nhận sự hiểu biết của AI có đúng không

### Kỹ thuật ba: Truyền tải theo khối

Không nên gửi lượng lớn thông tin một lần. Chia thành nhiều khối nhỏ, mỗi khối xác nhận AI hiểu rồi mới tiếp tục.

```
❌ Cách làm sai:
Gửi một lần tài liệu yêu cầu 3000 chữ

✅ Cách làm đúng:
Tin nhắn đầu: "Tôi muốn làm ứng dụng danh sách việc cần làm, trước tiên hãy định nghĩa cấu trúc dữ liệu cốt lõi..."
Đợi AI trả lời xác nhận
Tin nhắn thứ hai: "Cấu trúc dữ liệu xác định xong, tiếp theo là danh sách chức năng chính..."
```

**Hiệu quả**:
- Mỗi khối thông tin đều được xử lý đầy đủ
- Giảm xác suất AI bỏ sót thông tin
- Dễ phát hiện sai lệch hiểu biết kịp thời

### Kỹ thuật bốn: Nhắc lại thỏa thuận

Tại các điểm then chốt nhắc lại thỏa thuận quan trọng, đặc biệt là:
- Khi bắt đầu chức năng mới
- Khi phát hiện AI lệch khỏi thỏa thuận
- Khi đối thoại vượt quá 10 vòng

```markdown
Trước khi bắt đầu chức năng mới, xác nhận thỏa thuận của chúng ta:
1. Sử dụng TypeScript, không sử dụng type any
2. Component đặt trong thư mục src/components
3. Quản lý state dùng useState, state phức tạp dùng useReducer
4. Xử lý lỗi sử dụng try-catch

Xác nhận xong, hãy bắt đầu thực hiện [chức năng].
```

## Template thực dụng quản lý context

### Thiết lập context khi bắt đầu đối thoại

```markdown
Background dự án:
- Tên dự án: [tên]
- Tech stack: [danh sách tech stack]
- Tiến độ hiện tại: [mô tả ngắn gọn]

Nhiệm vụ lần này:
[mô tả nhiệm vụ cụ thể]

Hãy chú ý các thỏa thuận sau:
1. [thỏa thuận 1]
2. [thỏa thuận 2]
3. [thỏa thuận 3]
```

### "Checkpoint" giữa đối thoại dài

```markdown
Tạm dừng một chút, để tôi xác nhận trạng thái hiện tại:

Đã hoàn thành:
1. [chức năng 1]
2. [chức năng 2]

Kỹ thuật/thỏa thuận đang dùng:
- [thỏa thuận 1]
- [thỏa thuận 2]

Tiếp theo sẽ làm:
[nhiệm vụ tiếp theo]

Hiểu như trên có đúng không? Xác nhận rồi tiếp tục.
```

### Sửa lỗi khi vi phạm thỏa thuận

```markdown
Chú ý: Code vừa rồi sử dụng JavaScript, nhưng dự án chúng ta thỏa thuận sử dụng TypeScript.

Hãy tạo lại, và đảm bảo:
1. Tất cả biến và function đều có khai báo type
2. Không sử dụng type any
3. Export định nghĩa type để component khác sử dụng
```

## Quản lý context cấp công cụ

Ngoài quản lý context trong đối thoại, các AI IDE mainstream còn cung cấp chức năng **cấu hình bền vững**. Các cấu hình này sẽ tự động load khi bắt đầu mỗi cuộc đối thoại, để AI "sinh ra" đã biết quy chuẩn dự án của bạn.

### Bảng so sánh file cấu hình các công cụ mainstream

| Công cụ | Vị trí file cấu hình | Định vị chức năng |
|------|-------------|---------|
| **Cursor** | `.cursor/rules/*.mdc` | Quy chuẩn dự án, coding style, tech stack preference |
| **Windsurf** | `.windsurf/rules/*.md` hoặc `.windsurfrules` | Quy tắc hành vi AI cấp dự án |
| **Trae** | `.trae/project_rules.md`, `user_rules.md` | Quy tắc người dùng + quy tắc dự án |
| **Claude Code** | `CLAUDE.md` + `SKILL.md` | Context dự án + kỹ năng có thể tái sử dụng |
| **GitHub Copilot** | `.github/copilot-instructions.md` | Chỉ thị cấp repository |
| **OpenAI Codex** | `AGENTS.md` | File chỉ thị agent |
| **Factory Droid** | `.factory/droids/*.md` | Cấu hình Droid tùy chỉnh |
| **Aider** | `CONVENTIONS.md` | File quy chuẩn coding |
| **Cline** | `.clinerules` | Quy tắc dự án |

### File cấu hình nên viết gì?

Bất kể sử dụng công cụ nào, file cấu hình thường bao gồm:

1. **Tổng quan dự án**: Đây là dự án gì, giải quyết vấn đề gì
2. **Tech stack**: Ngôn ngữ, framework, thư viện đang sử dụng
3. **Quy chuẩn coding**: Quy ước đặt tên, code style, cấu trúc thư mục
4. **Điều cấm kỵ**: Thư viện không được dùng, pattern không được áp dụng
5. **Lệnh thường dùng**: Lệnh build, test, deploy

### Template cấu hình dự án chung

```markdown
# Cấu hình dự án

## Tổng quan dự án
Đây là ứng dụng danh sách việc cần làm, giúp người dùng quản lý nhiệm vụ hàng ngày.

## Tech stack
- Frontend: React 18 + TypeScript 5
- Style: Tailwind CSS 3
- Quản lý state: Zustand
- Test: Vitest

## Cấu trúc thư mục
- src/components: React component
- src/hooks: Custom Hooks
- src/utils: Hàm tiện ích
- src/types: Định nghĩa type TypeScript

## Quy chuẩn coding
- Sử dụng functional component, không dùng class component
- Tất cả function phải có khai báo type TypeScript
- File component sử dụng đặt tên PascalCase
- Hàm tiện ích sử dụng đặt tên camelCase
- Sử dụng comment tiếng Việt

## Điều cấm kỵ
- Không sử dụng type `any`
- Không sử dụng jQuery
- Không viết inline style trực tiếp trong component (dùng Tailwind)
- Không sử dụng `var`, dùng `const` hoặc `let`

## Lệnh thường dùng
- Phát triển: npm run dev
- Build: npm run build
- Test: npm test
```

### Tại sao file cấu hình rất quan trọng?

| Không có file cấu hình | Có file cấu hình |
|-------------|-----------|
| Mỗi lần đối thoại đều phải lặp lại tech stack | AI tự động biết tech stack |
| AI có thể dùng quy chuẩn sai | Quy chuẩn luôn nhất quán |
| Thành viên team cấu hình khác nhau | Team chia sẻ cùng một cấu hình |
| Thỏa thuận dễ bị quên | Thỏa thuận được kiểm soát phiên bản |

> **Gợi ý**: Phương pháp cấu hình chi tiết của từng công cụ cụ thể, hãy tham khảo tài liệu chính thức của các công cụ. Phiên bản cơ bản chỉ cần hiểu các chức năng này tồn tại là được, phiên bản nâng cao sẽ có hướng dẫn cấu hình công cụ chi tiết hơn.

## Điểm chính của tiểu mục

✓ **AI không có trí nhớ thực sự**: Nó nhìn thấy lịch sử đối thoại, lịch sử quá dài sẽ "tràn"

✓ **Tín hiệu tràn**: AI mất trí nhớ, tự mâu thuẫn, code style đột biến

✓ **Bốn kỹ thuật quản lý**: Thông tin then chốt đặt lên đầu, tóm tắt định kỳ, truyền tải theo khối, nhắc lại thỏa thuận

✓ **Cấu hình cấp công cụ**: Dùng file cấu hình để AI tự động load quy chuẩn dự án

✓ **Cộng tác team**: File cấu hình có thể đưa vào kiểm soát phiên bản, team chia sẻ

Tiểu mục tiếp theo, chúng ta sẽ học khi nào nên từ bỏ cuộc đối thoại cũ, bắt đầu một cuộc đối thoại hoàn toàn mới.
