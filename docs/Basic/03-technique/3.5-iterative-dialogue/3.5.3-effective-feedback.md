# 3.5.3 Nghệ thuật feedback hiệu quả

## Sau khi học tiểu mục này, bạn sẽ nắm vững

- Phân biệt feedback hiệu quả và feedback không hiệu quả
- Sử dụng framework SBI (Situation-Behavior-Impact) để tổ chức feedback
- Chọn độ chi tiết feedback phù hợp dựa trên loại vấn đề
- Có được một thư viện mẫu câu feedback có thể sử dụng trực tiếp

## Feedback quyết định chất lượng iteration

Cốt lõi của đối thoại iteration là vòng lặp "feedback-sửa". Chất lượng feedback bạn đưa ra quyết định trực tiếp chất lượng sửa của AI.

Cùng là không hài lòng với một đoạn code:

```
❌ Feedback không hiệu quả: "Không đúng, làm lại"
✅ Feedback hiệu quả: "Hàm handleSubmit thiếu xử lý lỗi, khi API request thất bại sẽ dẫn đến màn hình trắng"
```

Feedback loại thứ nhất, AI chỉ có thể đoán bạn không hài lòng điều gì. Feedback loại thứ hai, AI có thể định vị chính xác vấn đề và sửa.

## So sánh feedback không hiệu quả vs feedback hiệu quả

| Feedback không hiệu quả | Vấn đề | Feedback hiệu quả |
|---------|------|---------|
| "Không đúng" | Không biết sai chỗ nào | "Ở dòng 15 logic điều kiện sai, nên dùng `&&` thay vì `||`" |
| "Quá phức tạp" | Không biết cách đơn giản hóa | "Hãy xóa chức năng X và Y, chỉ giữ chức năng Z cốt lõi" |
| "Không đủ tốt" | Không biết tiêu chuẩn tốt | "Hãy tách hàm thành các đơn vị nhỏ hơn, mỗi hàm không quá 20 dòng" |
| "Style không đúng" | Không biết kỳ vọng style gì | "Màu button đổi thành #3B82F6, góc bo tròn đổi thành 8px" |
| "Có bug" | Không biết bug là gì | "Khi input vượt quá 100 ký tự, trang sẽ bị đơ" |

**Quy luật**: Feedback hiệu quả = Vị trí cụ thể + Vấn đề cụ thể + (Tùy chọn) Kết quả mong đợi

## Framework feedback SBI

SBI là một framework feedback từ lĩnh vực quản lý, sử dụng để đưa feedback cho AI cũng hiệu quả.

### Cấu trúc framework

```
S - Situation (Tình huống): Vấn đề xuất hiện ở đâu
B - Behavior (Hành vi): Cụ thể là vấn đề gì
I - Impact (Tác động): Vấn đề này sẽ dẫn đến hậu quả gì
```

### So sánh ví dụ

**Kịch bản**: Form AI tạo ra không có logic validation

```
❌ Không có SBI:
"Validation form có vấn đề"

✅ Sử dụng SBI:
"Trong hàm handleSubmit (S),
 không kiểm tra định dạng email có đúng không (B),
 điều này sẽ dẫn đến người dùng nhập email không hợp lệ vẫn có thể submit thành công (I).
 Hãy thêm validation định dạng email."
```

**Kịch bản**: Code AI tạo ra có hiệu suất kém

```
❌ Không có SBI:
"Code quá chậm"

✅ Sử dụng SBI:
"Trong hàm renderList (S),
 mỗi lần render đều tạo lại toàn bộ mảng (B),
 điều này sẽ dẫn đến khi danh sách có 100 items trang bị lag rõ rệt (I).
 Hãy sử dụng useMemo để tối ưu."
```

### Phiên bản đơn giản hóa SBI

Đối với vấn đề đơn giản, có thể bỏ qua Impact:

```
"Trong hàm handleAdd (S), thiếu kiểm tra input rỗng (B). Hãy thêm validation."
```

## Kim tự tháp độ chi tiết feedback

Các loại vấn đề khác nhau cần độ chi tiết feedback khác nhau.

```
        ▲
       ╱ ╲
      ╱   ╲     Feedback cấp hướng
     ╱ Hướng ╲    "Tư duy tổng thể cần điều chỉnh"
    ╱───────╲
   ╱  Chức năng   ╲   Feedback cấp chức năng
  ╱───────────╲  "Chức năng này thiếu XX"
 ╱    Code     ╲  Feedback cấp code
╱───────────────╲ "Dòng 15 nên đổi thành XX"
```

### Feedback cấp hướng

**Tình huống sử dụng**: Tư duy tổng thể của AI lệch khỏi kỳ vọng của bạn

**Đặc điểm**:
- Không quan tâm chi tiết
- Mô tả lại hướng lớn mong đợi
- Có thể cần lật đổ làm lại

**Ví dụ**:
```
Tôi cần không phải một trang mới, mà là một popup component.
Hãy thực hiện lại: người dùng click button sau đó, hiện popup modal cho người dùng nhập nhiệm vụ.
```

### Feedback cấp chức năng

**Tình huống sử dụng**: Hướng đúng, nhưng chức năng cụ thể có thiếu sót hoặc lỗi

**Đặc điểm**:
- Nhắm vào điểm chức năng cụ thể
- Giữ lại phần đã đúng
- Sửa đổi tăng dần

**Ví dụ**:
```
Chức năng tổng thể được, hãy bổ sung nội dung sau:
1. Thêm button hủy, click sau đó đóng popup
2. Click vùng ngoài popup cũng có thể đóng
3. Nhấn phím ESC cũng có thể đóng
```

### Feedback cấp code

**Tình huống sử dụng**: Chức năng đúng, nhưng chi tiết code cần điều chỉnh

**Đặc điểm**:
- Chính xác đến số dòng hoặc tên hàm
- Đưa ra chỉ thị sửa đổi rõ ràng
- Thay đổi phạm vi tối thiểu

**Ví dụ**:
```
Hãy sửa các chi tiết sau:
1. Dòng 23: Đổi `var` thành `const`
2. Hàm handleClose: Thêm event.stopPropagation() để ngăn event bubbling
3. Component Modal: Thêm aria-label="popup nhập nhiệm vụ" để nâng cao accessibility
```

### Chọn độ chi tiết phù hợp

| Loại vấn đề | Độ chi tiết sử dụng | Tiêu chuẩn đánh giá |
|---------|---------|---------|
| AI hiểu sai yêu cầu | Cấp hướng | Cần lật đổ làm lại |
| Thiếu chức năng/lỗi logic | Cấp chức năng | Giữ phần lớn, sửa tăng dần |
| Vấn đề style/chi tiết code | Cấp code | Chỉ cần điều chỉnh nhỏ |

## Thư viện mẫu câu feedback cho các kịch bản thường gặp

### Thiếu chức năng

```markdown
Hãy bổ sung các chức năng sau:
1. [mô tả chức năng]
2. [mô tả chức năng]
```

```markdown
Implementation này thiếu [tên chức năng].
Yêu cầu cụ thể: [mô tả chi tiết]
```

### Lỗi logic

```markdown
[tên hàm/vị trí] có lỗi logic:
- Hành vi hiện tại: [mô tả hành vi lỗi hiện tại]
- Hành vi mong đợi: [mô tả hành vi đúng]
- Hãy sửa.
```

```markdown
Trong trường hợp [kịch bản], [vấn đề cụ thể].
Logic đúng nên là: [mô tả logic đúng]
```

### Tối ưu cấu trúc code

```markdown
Hãy tối ưu cấu trúc code sau:
1. Tách [mô tả logic] thành hàm độc lập
2. Di chuyển [nội dung] đến [vị trí]
3. [điều chỉnh cấu trúc khác]
```

```markdown
Hàm này quá dài (hiện tại [X] dòng), hãy tách thành:
- [hàm 1]: chịu trách nhiệm [nhiệm vụ]
- [hàm 2]: chịu trách nhiệm [nhiệm vụ]
```

### Điều chỉnh style

```markdown
Hãy sửa các style sau:
- [phần tử]: [thuộc tính] đổi thành [giá trị]
- [phần tử]: [thuộc tính] đổi thành [giá trị]
```

```markdown
Style của [component] cần điều chỉnh:
1. [vấn đề style cụ thể]
2. [vấn đề style cụ thể]
Tham khảo thiết kế: [mô tả hoặc link ảnh]
```

### Trường hợp biên

```markdown
Hãy xử lý các trường hợp biên sau:
1. Khi [điều kiện], nên [hành vi]
2. Khi [điều kiện], nên [hành vi]
```

```markdown
Implementation hiện tại không xem xét [trường hợp biên].
Khi [kịch bản cụ thể] xảy ra, sẽ [mô tả vấn đề].
Hãy thêm logic xử lý tương ứng.
```

## Ví dụ thực chiến: Sửa một đoạn code có vấn đề

**Code vòng đầu AI đưa ra**:
```tsx
function TaskList({ tasks }) {
  return (
    <ul>
      {tasks.map(task => (
        <li onClick={() => deleteTask(task.id)}>
          {task.title}
        </li>
      ))}
    </ul>
  );
}
```

**Phân tích vấn đề**:
1. Thiếu type TypeScript
2. Thiếu key trong map
3. deleteTask chưa được định nghĩa
4. Click toàn bộ li là xóa, tương tác không hợp lý

**Feedback hiệu quả**:
```markdown
Hãy sửa các vấn đề sau:

1. Định nghĩa type:
   - Thêm định nghĩa interface Task (id: string, title: string)
   - Thêm type cho parameter tasks

2. Cảnh báo React:
   - li trong map cần thêm key={task.id}

3. Vấn đề chức năng:
   - Hàm deleteTask chưa được định nghĩa, hãy truyền vào qua props
   - Không nên để toàn bộ li click để xóa, đổi thành: thêm một button xóa sau mỗi nhiệm vụ

4. An toàn tương tác:
   - Thêm xác nhận trước khi xóa
```

## Lưu ý khi feedback

### Một lần không nên feedback quá nhiều

```
❌ Một lần đưa ra 10 điểm sửa đổi
✅ Một lần đưa ra 3-5 điểm sửa đổi có liên quan
```

Nếu vấn đề nhiều, ưu tiên feedback những vấn đề quan trọng nhất, thực hiện theo batch.

### Feedback phải cụ thể, nhưng không nên chỉ định quá mức

```
❌ Chỉ định quá mức: "Ở giữa dòng 15 và dòng 16 chèn const x = 1;"
✅ Cụ thể vừa phải: "Trong handleSubmit thêm kiểm tra giá trị rỗng"
```

Nói với AI "làm cái gì", thay vì "viết từng dòng code như thế nào".

### Giải thích "tại sao" đôi khi rất hữu ích

```
Hãy tách hàm validateInput ra ngoài.
Lý do: Logic validation này cũng sẽ được dùng trong form khác, tách thành hàm độc lập để tái sử dụng dễ dàng.
```

AI hiểu ý định của bạn sau có thể đưa ra implementation tốt hơn.

## Điểm chính của tiểu mục

✓ **Ba yếu tố feedback hiệu quả**: Vị trí cụ thể + Vấn đề cụ thể + Kết quả mong đợi

✓ **Framework SBI**: Situation (đâu) → Behavior (vấn đề gì) → Impact (dẫn đến gì)

✓ **Kim tự tháp độ chi tiết**: Cấp hướng → Cấp chức năng → Cấp code, chọn theo loại vấn đề

✓ **Thư viện mẫu câu**: Tích lũy các mẫu câu feedback thường dùng, nâng cao hiệu quả giao tiếp

✓ **Nguyên tắc tiết chế**: Một lần 3-5 điểm sửa đổi, nói "làm gì" thay vì "viết thế nào"

Tiểu mục tiếp theo, chúng ta sẽ học cách quản lý context trong đối thoại dài, tránh AI "mất trí nhớ".
