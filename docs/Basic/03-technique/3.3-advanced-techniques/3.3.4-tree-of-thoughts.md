# 3.3.4 Tree of Thoughts: Khám phá nhiều đường suy luận

> **Lưu ý định vị**: Đây là kỹ thuật nâng cao tùy chọn. Trong Vibe Coding hàng ngày, hầu hết tình huống dùng Zero-shot, Few-shot, CoT là đủ. Tree of Thoughts chủ yếu dùng cho **lựa chọn công nghệ, quyết định kiến trúc** và các tình huống cần so sánh nhiều phương án, chiếm khoảng 5% công việc hàng ngày. Nếu bạn mới bắt đầu, có thể bỏ qua phần này trước, gặp nhu cầu rồi quay lại tra cứu.

## Qua phần này bạn sẽ nắm được

- Định nghĩa và tình huống áp dụng của Tree of Thoughts (ToT)
- Sự khác biệt giữa ToT và Chain of Thought
- Cách sử dụng ToT phiên bản đầy đủ và rút gọn
- Khi nào cần ToT, khi nào không cần

## Tree of Thoughts là gì

Ý tưởng cốt lõi của Tree of Thoughts (cây suy nghĩ, viết tắt ToT) là: **Để AI khám phá nhiều đường đi có thể, so sánh rồi chọn phương án tối ưu**.

Nếu ví Chain of Thought là "đi một con đường đến cuối", thì Tree of Thoughts là "xem trước có mấy con đường, so sánh rồi quyết định đi đường nào".

```
Chain of Thought (tuyến tính):
Vấn đề → Bước 1 → Bước 2 → Bước 3 → Câu trả lời

Tree of Thoughts (dạng cây):
Vấn đề → Phương án A → Đánh giá A
     → Phương án B → Đánh giá B  → So sánh → Đề xuất tối ưu
     → Phương án C → Đánh giá C
```

## Sự khác biệt giữa ToT và CoT

| Chiều | Chain of Thought | Tree of Thoughts |
|-----|-----------------|------------------|
| Đường suy luận | Đường duy nhất | Nhiều đường song song |
| Tình huống áp dụng | Vấn đề có đáp án chuẩn | Quyết định cần cân nhắc so sánh |
| Hình thức output | Suy diễn từng bước đến kết luận | So sánh nhiều phương án rồi đề xuất |
| Tiêu thụ token | Trung bình | Khá cao |
| Tần suất dùng hàng ngày | Cao (khoảng 30%) | Thấp (khoảng 5%) |

**Đề xuất lựa chọn**:
- Nếu vấn đề có "đáp án đúng" → Dùng CoT
- Nếu cần "chọn phương án tối ưu" → Dùng ToT

## Tình huống áp dụng cốt lõi

ToT phù hợp nhất với các tình huống sau:

### 1. Lựa chọn công nghệ

Chọn database, framework, dịch vụ bên thứ ba, v.v.

### 2. Quyết định kiến trúc

Thiết kế kiến trúc hệ thống, phong cách API, mô hình dữ liệu, v.v.

### 3. So sánh phương án

Phân tích ưu nhược điểm của nhiều cách implement.

### 4. Phân rã vấn đề phức tạp

Vấn đề cần tiếp cận từ nhiều góc độ.

## Prompt kém vs Prompt tốt

### Tình huống: Chọn phương án lưu trữ dữ liệu cho todo list

### ❌ Prompt kém

```
Ứng dụng todo list của tôi nên dùng cách nào để lưu trữ dữ liệu?
```

**Vấn đề**: AI có thể chỉ đề xuất một phương án, không có phân tích so sánh.

### ✅ Prompt tốt (dùng ToT)

```
Tôi đang làm một ứng dụng todo list cá nhân, cần chọn phương án lưu trữ dữ liệu.

Bối cảnh dự án:
- Số người dùng: chỉ bản thân sử dụng
- Lượng dữ liệu: dự kiến vài trăm task
- Cách deploy: static web hosting (như Vercel)
- Tech stack: React + TypeScript

Vui lòng đưa ra 3 phương án lưu trữ khác nhau, phân tích từng phương án:
1. Độ phức tạp implement (1-5 điểm, 5 điểm là phức tạp nhất)
2. Tính bền vững dữ liệu
3. Có cần backend không
4. Tình huống phù hợp

Cuối cùng, dựa trên tình hình dự án của tôi, đề xuất phương án phù hợp nhất và nêu lý do.
```

### Output AI với prompt tốt

```
## Phân tích phương án

### Phương án một: localStorage
- Độ phức tạp implement: 1 điểm
- Tính bền vững dữ liệu: chỉ local browser, đổi thiết bị thì mất
- Có cần backend: không
- Tình huống phù hợp: công cụ cá nhân, xác minh prototype

### Phương án hai: IndexedDB
- Độ phức tạp implement: 3 điểm
- Tính bền vững dữ liệu: local browser, hỗ trợ lượng dữ liệu lớn hơn
- Có cần backend: không
- Tình huống phù hợp: ứng dụng local cần lưu nhiều dữ liệu có cấu trúc

### Phương án ba: Supabase (cloud database)
- Độ phức tạp implement: 3 điểm
- Tính bền vững dữ liệu: lưu trữ cloud, đồng bộ nhiều thiết bị
- Có cần backend: không (dịch vụ BaaS)
- Tình huống phù hợp: cần đồng bộ nhiều thiết bị, có kế hoạch mở rộng

## Phương án đề xuất

Dựa trên tình hình của bạn (chỉ bản thân dùng, vài trăm dữ liệu, static hosting), đề xuất **Phương án một: localStorage**.

Lý do:
1. Implement đơn giản nhất, vài dòng code là được
2. Lượng dữ liệu nhỏ, localStorage hoàn toàn đủ dùng
3. Không cần dịch vụ phụ, phù hợp yêu cầu static hosting
4. Làm MVP xác minh nhanh, sau này có nhu cầu rồi nâng cấp

Nếu sau này cần đồng bộ nhiều thiết bị, có thể chuyển sang Supabase.
```

## Ví dụ thực chiến: Lựa chọn phương án chức năng login

Todo list của Tiểu Lý cần thêm chức năng login, anh ấy muốn so sánh vài cách implement.

### Prompt ToT

```
Ứng dụng todo list của tôi cần thêm chức năng login người dùng.

Bối cảnh dự án:
- Dự án cá nhân, số người dùng dự kiến < 100 người
- Tech stack: Next.js + TypeScript
- Deploy trên Vercel
- Hy vọng implement càng đơn giản càng tốt

Vui lòng phân tích ba phương án login sau:
1. Login username password truyền thống
2. Login mã xác thực điện thoại
3. Login OAuth bên thứ ba (như GitHub, Google)

Phân tích từng phương án:
- Độ phức tạp implement
- Trải nghiệm người dùng
- Bảo mật
- Chi phí maintain

Cuối cùng đề xuất một phương án, và nêu lý do.
```

### Điểm chính output AI

AI sẽ phân tích ưu nhược điểm của ba phương án, và dựa trên bối cảnh "dự án cá nhân, số người dùng ít, mong muốn đơn giản", đề xuất phương án phù hợp nhất (có thể là OAuth bên thứ ba, vì không phải tự quản lý mật khẩu).

## ToT rút gọn: Sử dụng nhanh hàng ngày

Nếu không cần so sánh đầy đủ nhiều phương án, có thể dùng phiên bản rút gọn:

```
Vui lòng đưa ra 2-3 hướng implement khác nhau, so sánh ngắn gọn ưu nhược điểm rồi đề xuất một.
```

Cách này output ngắn gọn hơn, phù hợp quyết định nhanh hàng ngày.

### Ví dụ phiên bản rút gọn

```
Tôi muốn implement chức năng sắp xếp task kéo thả, vui lòng đưa ra 2-3 hướng implement, so sánh ngắn gọn rồi đề xuất một.
Tech stack: React + TypeScript
```

### Output phiên bản rút gọn

```
Ba hướng implement:

1. react-beautiful-dnd
   Ưu điểm: chức năng đầy đủ, animation mượt
   Nhược điểm: kích thước package lớn, đã ngưng maintain

2. @dnd-kit
   Ưu điểm: thiết kế hiện đại, kích thước nhỏ, maintain tích cực
   Nhược điểm: learning curve hơi dốc

3. HTML5 Drag API gốc
   Ưu điểm: không phụ thuộc
   Nhược điểm: cần nhiều code, hiệu ứng animation phải tự implement

Đề xuất: @dnd-kit
Lý do: hiện đại, nhẹ, cộng đồng tích cực, phù hợp dự án maintain lâu dài.
```

## Khi nào không cần ToT

| Tình huống | Dùng ToT? | Lý do |
|-----|---------|------|
| Implement một chức năng cụ thể | ❌ | Viết code trực tiếp là được |
| Sửa một Bug | ❌ | Dùng CoT kiểm tra từng bước |
| Format output | ❌ | Dùng Few-shot |
| Lựa chọn công nghệ | ✅ | Cần so sánh nhiều lựa chọn |
| Thiết kế kiến trúc | ✅ | Cần cân nhắc nhiều phương án |

**Tiêu chuẩn đánh giá**: Nếu trong đầu bạn đã có hướng đi đại khái, chỉ muốn xác nhận, không cần ToT. Nếu cần AI giúp bạn "đưa ra lựa chọn", dùng ToT.

## Template có thể sao chép

### Template ToT đầy đủ

```markdown
Tôi cần [nội dung quyết định].

Bối cảnh dự án:
- [thông tin bối cảnh 1]
- [thông tin bối cảnh 2]
- [ràng buộc quan trọng]

Vui lòng đưa ra [số lượng] phương án khác nhau, phân tích từng phương án:
1. [chiều đánh giá 1]
2. [chiều đánh giá 2]
3. [chiều đánh giá 3]
4. [chiều đánh giá 4]

Cuối cùng, dựa trên tình hình dự án của tôi, đề xuất phương án phù hợp nhất và nêu lý do.
```

### Template ToT rút gọn

```markdown
Tôi muốn [mục tiêu implement].
Bối cảnh: [bối cảnh ngắn gọn]

Vui lòng đưa ra 2-3 hướng khác nhau, so sánh ngắn gọn ưu nhược điểm rồi đề xuất một.
```

### Template chuyên dụng lựa chọn công nghệ

```markdown
Tôi cần chọn [loại lựa chọn: database/framework/dịch vụ bên thứ ba].

Tình hình dự án:
- Quy mô: [số người dùng/lượng dữ liệu]
- Tech stack: [công nghệ hiện có]
- Cách deploy: [môi trường deploy]
- Tình hình team: [trình độ kỹ thuật/số người]

Chiều đánh giá:
- Độ phức tạp implement
- Hiệu suất
- Chi phí maintain
- Hệ sinh thái cộng đồng

Vui lòng so sánh [danh sách phương án ứng viên], đề xuất lựa chọn phù hợp nhất.
```

## Những điểm chính của phần này

✓ **Bản chất của ToT**: Khám phá nhiều đường đi, so sánh rồi chọn phương án tối ưu

✓ **Khác với CoT**: CoT là suy luận đường duy nhất, ToT là so sánh nhiều phương án

✓ **Tình huống áp dụng**: Lựa chọn công nghệ, quyết định kiến trúc, so sánh phương án (chiếm khoảng 5%)

✓ **Phiên bản rút gọn**: Sử dụng nhanh hàng ngày "đưa ra 2-3 hướng, so sánh rồi đề xuất"

✓ **Đừng lạm dụng**: Nếu đã có hướng đi, thực hiện trực tiếp là được

Phần tiếp theo, chúng ta sẽ học cách để AI tự kiểm tra—Self-Critique.
