# 3.3.3 Chain of Thought: Để AI "suy nghĩ" rồi mới trả lời

## Qua phần này bạn sẽ nắm được

- Định nghĩa và nguyên lý của Chain of Thought (CoT)
- Hai cách kích hoạt CoT
- Tình huống CoT thực sự hiệu quả (dựa trên nghiên cứu mới nhất)
- Cách viết prompt CoT hiệu quả
- Hạn chế và lưu ý khi dùng CoT

## Chain of Thought là gì

Ý tưởng cốt lõi của Chain of Thought (chuỗi suy nghĩ, viết tắt CoT) là: **Để AI viết ra quá trình suy luận, thay vì đưa câu trả lời trực tiếp**.

Giống như bài thi toán yêu cầu "viết các bước giải", khi AI được yêu cầu trình bày quá trình suy nghĩ, thường sẽ có câu trả lời chính xác hơn.

```
❌ Hỏi trực tiếp:
Độ phức tạp thời gian của function này là bao nhiêu?

✅ Dùng CoT:
Vui lòng phân tích độ phức tạp thời gian của function này.
Đầu tiên, xác định cấu trúc vòng lặp trong code;
Sau đó, phân tích số lần thực hiện của mỗi vòng lặp;
Cuối cùng, tính tổng độ phức tạp thời gian.
```

## Hiểu biết cốt lõi: CoT không phải vạn năng

> "Chain of Thought chủ yếu có hiệu quả rõ rệt trên các task toán học và suy luận ký hiệu, lợi ích hạn chế với các loại task khác."
> —— Bài báo 2024 "To CoT or not to CoT?"

Kết luận nghiên cứu này rất quan trọng. Nó cho chúng ta biết:

| Loại task | Hiệu quả CoT | Lý do |
|---------|---------|------|
| Tính toán toán học | ✅ Cải thiện rõ rệt | Cần suy luận nhiều bước, phân tách bước có giúp ích |
| Suy luận logic | ✅ Cải thiện rõ ràng | Logic phức tạp cần lược qua từng bước |
| Phân tích code | ✅ Có giúp ích | Liên quan đến nhiều lớp lồng nhau và điều kiện |
| Tạo văn bản | ⚠️ Lợi ích hạn chế | Task sáng tạo không cần suy luận nghiêm ngặt |
| Phân loại đơn giản | ❌ Có thể chậm hơn | Tăng các bước không cần thiết |

**Đề xuất thực hành**: Đừng dùng CoT cho tất cả task, chỉ dùng trong tình huống cần suy luận.

## Hai cách kích hoạt

### Cách một: Câu thần chú

Cách đơn giản nhất, chỉ cần thêm một câu ở cuối prompt:

```
Vui lòng phân tích điểm nghẽn hiệu suất của đoạn code này.
Let's think step by step.
```

Hoặc phiên bản tiếng Việt:

```
Vui lòng phân tích điểm nghẽn hiệu suất của đoạn code này.
Hãy suy nghĩ từng bước một.
```

Cách này đơn giản, nhưng các bước suy luận của AI có thể thiếu cấu trúc.

### Cách hai: Phân tách bước rõ ràng

Cách kiểm soát tốt hơn, nói trực tiếp cho AI phải chia bước như thế nào:

```
Vui lòng phân tích điểm nghẽn hiệu suất của đoạn code này.

Các bước phân tích:
1. Đầu tiên, xác định cấu trúc vòng lặp và đệ quy trong code
2. Sau đó, tìm ra các phép tính có thể lặp lại
3. Tiếp theo, kiểm tra xem lựa chọn cấu trúc dữ liệu có hợp lý không
4. Cuối cùng, đưa ra đề xuất tối ưu và hiệu quả dự kiến
```

Cách này output có cấu trúc hơn, phù hợp với tình huống cần góc nhìn phân tích cụ thể.

## Prompt kém vs Prompt tốt

### Tình huống: Phân tích logic validate form

### ❌ Prompt kém

```
Logic validate form này có vấn đề không?

function validateForm(data) {
  if (data.email && data.password && data.password.length >= 6) {
    if (data.email.includes('@')) {
      return true;
    }
  }
  return false;
}
```

**Vấn đề**: AI có thể chỉ đưa ra kết luận chung chung, bỏ qua một số trường hợp biên.

### ✅ Prompt tốt (dùng CoT)

```
Vui lòng review function validate form này, kiểm tra xem có thiếu sót tình huống validate nào không.

function validateForm(data) {
  if (data.email && data.password && data.password.length >= 6) {
    if (data.email.includes('@')) {
      return true;
    }
  }
  return false;
}

Các bước phân tích:
1. Đầu tiên, liệt kê các điều kiện mà function này hiện tại đang kiểm tra
2. Sau đó, suy nghĩ validate form thông thường cần kiểm tra gì
3. Tiếp theo, so sánh tìm ra các mục validate bị thiếu
4. Cuối cùng, đưa ra đề xuất cải thiện
```

### Output AI với prompt tốt

```
Quá trình phân tích:

1. Điều kiện hiện tại đang kiểm tra:
   - email tồn tại và không rỗng
   - password tồn tại và không rỗng
   - độ dài password >= 6
   - email chứa ký hiệu @

2. Validate form thông thường cần kiểm tra:
   - tính đầy đủ format email (trước và sau @ đều phải có nội dung, phải có tên miền)
   - độ mạnh password (chữ hoa thường, số, ký tự đặc biệt)
   - phòng chống SQL injection và XSS
   - xử lý khoảng trắng

3. Các mục validate bị thiếu:
   - format email không đầy đủ: "@" hoặc "a@" hoặc "@b" đều có thể pass
   - password chỉ kiểm tra độ dài, không kiểm tra độ mạnh
   - không xử lý khoảng trắng đầu cuối
   - không validate tên miền của email (như .com)

4. Đề xuất cải thiện:
   - Dùng regex validate format email
   - Thêm kiểm tra độ mạnh password
   - Xử lý input bằng trim()
```

## Bảng quyết định tình huống áp dụng

| Tình huống | Có dùng CoT | Lý do |
|-----|------------|------|
| Tính độ phức tạp thời gian/không gian | ✅ Dùng | Cần phân tích vòng lặp lồng nhau |
| Review logic code | ✅ Dùng | Cần xét nhiều nhánh và biên |
| Thiết kế cấu trúc bảng database | ✅ Dùng | Cần phân tích quan hệ entity |
| Debug nguyên nhân lỗi | ✅ Dùng | Cần kiểm tra từng bước |
| Chuyển đổi format code đơn giản | ❌ Không | Chuyển đổi trực tiếp là được |
| Viết một đoạn content | ❌ Không | Task sáng tạo không cần suy luận nghiêm ngặt |
| Đổi tên biến | ❌ Không | Task quá đơn giản |

## Ví dụ thực chiến: Dự án todo list

Tiểu Lý muốn AI giúp phân tích một Bug: sau khi xóa task, đôi khi trang không cập nhật.

### Prompt CoT

```
Ứng dụng todo list của tôi có một Bug: sau khi xóa task, trang đôi khi không cập nhật.

Sau đây là code liên quan:

// State danh sách task
const [tasks, setTasks] = useState([]);

// Xóa task
const deleteTask = (id) => {
  tasks.splice(tasks.findIndex(t => t.id === id), 1);
  setTasks(tasks);
}

Vui lòng giúp tôi phân tích nguyên nhân vấn đề.

Các bước phân tích:
1. Đầu tiên, hiểu cơ chế cập nhật state của React
2. Sau đó, kiểm tra cách cập nhật state của đoạn code này
3. Tiếp theo, tìm ra nguyên nhân dẫn đến không cập nhật
4. Cuối cùng, đưa ra phương án sửa lỗi
```

### Output của AI

```
Quá trình phân tích:

1. Cơ chế cập nhật state của React:
   React quyết định có re-render hay không bằng cách so sánh reference của state mới và cũ.
   Nếu reference của object state không thay đổi, React cho là state không thay đổi.

2. Vấn đề của code hiện tại:
   - splice() sửa đổi trực tiếp mảng gốc
   - setTasks(tasks) truyền vào vẫn là reference mảng đó
   - React so sánh thấy reference giống nhau, không kích hoạt re-render

3. Nguyên nhân gốc rễ:
   Sửa đổi trực tiếp mảng gốc (mutation) thay vì tạo mảng mới (immutation)

4. Phương án sửa lỗi:
   Dùng filter tạo mảng mới:

   const deleteTask = (id) => {
     setTasks(tasks.filter(t => t.id !== id));
   }

   Hoặc dùng spread operator:

   const deleteTask = (id) => {
     const newTasks = [...tasks];
     newTasks.splice(newTasks.findIndex(t => t.id === id), 1);
     setTasks(newTasks);
   }
```

## Concise CoT: Phiên bản ngắn gọn

Nếu muốn tiết kiệm token, có thể dùng CoT ngắn gọn:

```
Vui lòng phân tích ngắn gọn độ phức tạp thời gian của function này, dùng 2-3 câu giải thích quá trình suy luận, sau đó đưa ra kết luận.
```

Nghiên cứu cho thấy, Concise CoT có thể giảm khoảng 50% độ dài output, đồng thời giữ được phần lớn độ chính xác suy luận.

## Hạn chế của CoT

| Hạn chế | Biểu hiện | Cách ứng phó |
|-----|------|---------|
| Tăng độ dài output | Tiêu thụ token tăng 20-80% | Dùng Concise CoT hoặc giới hạn số chữ |
| Một số task lại kém đi | Task đơn giản ép chia bước có thể sai | Chọn có dùng hay không dựa trên tình huống |
| Suy luận có thể sai | Một bước sai, sau này toàn sai | Kết hợp Self-Critique để kiểm tra |

## Template có thể sao chép

### Template CoT phân tích code

```markdown
Vui lòng phân tích [mục tiêu phân tích: hiệu suất/bảo mật/khả năng maintain] của code sau:

[code]

Các bước phân tích:
1. Đầu tiên, [góc độ phân tích bước một]
2. Sau đó, [góc độ phân tích bước hai]
3. Tiếp theo, [góc độ phân tích bước ba]
4. Cuối cùng, đưa ra kết luận và đề xuất
```

### Template CoT kiểm tra vấn đề

```markdown
Mô tả vấn đề: [hiện tượng vấn đề]

Code/config liên quan:
[code hoặc config]

Vui lòng giúp tôi phân tích nguyên nhân vấn đề.

Các bước kiểm tra:
1. Đầu tiên, hiểu tình huống bình thường nên hoạt động như thế nào
2. Sau đó, kiểm tra luồng thực thi của code hiện tại
3. Tiếp theo, xác định khâu có thể dẫn đến vấn đề
4. Cuối cùng, đưa ra phương án sửa lỗi
```

### Template CoT ngắn gọn

```markdown
Vui lòng phân tích [task].
Dùng 2-3 câu giải thích quá trình suy luận, sau đó đưa ra kết luận.
```

## Những điểm chính của phần này

✓ **Bản chất của CoT**: Để AI trình bày quá trình suy luận, thay vì đưa câu trả lời trực tiếp

✓ **Tình huống hiệu quả**: Tính toán toán học, suy luận logic, phân tích code, kiểm tra vấn đề

✓ **Hai cách kích hoạt**: Câu thần chú (đơn giản) vs Phân tách bước rõ ràng (kiểm soát được)

✓ **Đừng lạm dụng**: Task đơn giản không cần CoT, ngược lại còn giảm hiệu suất

✓ **Concise CoT**: Khi cần tiết kiệm token thì dùng phiên bản ngắn gọn

Phần tiếp theo, chúng ta sẽ học cách để AI khám phá nhiều đường đi—Tree of Thoughts.
