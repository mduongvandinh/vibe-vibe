# 3.6.4 Chiến lược dự phòng: Khi AI thực sự không làm được

## Sau khi học xong phần này, bạn sẽ nắm được

- Nhận diện ranh giới khả năng của AI
- 3 phương án dự phòng và tình huống áp dụng
- Phương pháp vận hành của mô hình "phát triển kết hợp"
- Biết khi nào nên tìm kiếm sự trợ giúp bên ngoài

## Nhận biết ranh giới khả năng của AI

AI rất mạnh, nhưng không phải vạn năng. Hiểu được ranh giới của nó, giúp bạn đưa ra quyết định đúng đắn ở thời điểm quan trọng, tránh lãng phí thời gian trong ngõ cụt.

### Việc AI làm giỏi

| Lĩnh vực | Task cụ thể |
|-----|---------|
| **Code chuẩn hóa** | Implement chức năng phổ biến, chuyển đổi format dữ liệu, sinh template code |
| **Tài liệu và giải thích** | Giải thích logic code, sinh comment, viết tài liệu |
| **Nhận dạng pattern** | Nhận diện vấn đề code, tìm giải pháp tương tự, đề xuất refactor |
| **Prototype nhanh** | Sinh UI component, dựng khung dự án, implement MVP |

### Việc AI không làm giỏi

| Lĩnh vực | Nguyên nhân | Ví dụ |
|-----|------|------|
| **Cấu hình môi trường phức tạp** | Liên quan đến đường dẫn local, quyền hệ thống, cấu hình mạng mà AI không thể truy cập | Cấu hình mạng Docker, thiết lập biến môi trường |
| **Task cần xác minh thời gian thực** | AI không thể thực sự chạy code để xác minh kết quả | Debug vấn đề performance, tìm memory leak |
| **Logic đặc thù dự án cao** | Phụ thuộc context dự án nhiều, vượt quá dung lượng cửa sổ đối thoại | Quy tắc business phức tạp, tích hợp legacy system |
| **Thao tác nhạy cảm về bảo mật** | Liên quan đến key, credential không nên lộ | Cấu hình API key, xử lý mật khẩu người dùng |
| **Thao tác dữ liệu thời gian thực** | Không thể truy cập database thực, API ngoài | Migration database, troubleshoot vấn đề production |

### Nhận diện tín hiệu "AI không làm được"

- 🚨 Bạn đã cung cấp tất cả context nghĩ ra được, AI vẫn không cho câu trả lời đúng
- 🚨 AI liên tục đưa ra phương án "trông đúng nhưng thực tế không dùng được"
- 🚨 Vấn đề liên quan đến nội dung bạn không thể mô tả bằng văn bản (như hiệu ứng visual, môi trường local)
- 🚨 Sửa đổi trên 5 vòng, vấn đề vẫn chưa giải quyết

## Ba phương án dự phòng

### Phương án một: Đổi công cụ AI

Các mô hình AI khác nhau có dữ liệu huấn luyện và lĩnh vực chuyên môn khác nhau. Nếu một công cụ liên tục bị kẹt, đổi một cái khác thử thường hiệu quả.

**Đề xuất lựa chọn**:

| Loại task | Phương án thay thế có thể thử |
|---------|----------------|
| Liên quan frontend/React | AI khác nhau có thể có sở thích framework khác nhau |
| Vấn đề logic thuật toán | Thử mô hình AI thiên về lý thuyết |
| Giải thích code và học tập | Chọn AI giỏi dạy học |
| Prototype nhanh | Chọn công cụ sinh code nhanh |

**Điểm lưu ý khi vận hành**:
- Khi đổi công cụ, hãy sắp xếp lại mô tả nhu cầu
- Đừng mang code sai của AI trước sang (tránh gây nhiễu)
- Chỉ mô tả bản thân vấn đề và kết quả mong đợi

### Phương án hai: Dùng search engine tìm giải pháp có sẵn

Nhiều vấn đề đã được người khác gặp và giải quyết rồi. Dùng search engine tìm giải pháp có sẵn có thể đáng tin hơn việc để AI sinh từ đầu.

**Kỹ thuật search hiệu quả**:

```
[Từ khóa thông báo lỗi] site:stackoverflow.com
```

```
[Tech stack] [Mô tả chức năng] github
```

```
[Tên thư viện] [Vấn đề cụ thể] tài liệu chính thức
```

**Ví dụ**:
```
TypeError map undefined react site:stackoverflow.com
```

**Sau đó để AI giúp bạn hiểu và adapt**:
```markdown
Tôi tìm được giải pháp này trên Stack Overflow:

[Paste code tìm được]

Vui lòng giúp tôi:
1. Giải thích nguyên lý của đoạn code này
2. Căn cứ vào tình hình dự án của tôi ([Mô tả tech stack của bạn]) sửa đổi phù hợp
```

### Phương án ba: Dùng AI để hiểu concept, tự tay implement

Khi code AI sinh không đáng tin, có thể lùi một bước - để nó giúp bạn hiểu nguyên lý, rồi bạn tự viết code.

**Quy trình vận hành**:

1. **Để AI giải thích nguyên lý**:
   ```markdown
   Đừng viết code. Vui lòng giải thích nguyên lý hoạt động của [concept/chức năng], bao gồm:
   - Tư tưởng cốt lõi là gì
   - Có những bước chính nào
   - Có những hố nào thường gặp cần chú ý
   ```

2. **Để AI cung cấp pseudocode**:
   ```markdown
   Vui lòng dùng pseudocode (không phải code thật) mô tả các bước implement,
   để tôi hiểu logic tổng thể.
   ```

3. **Bạn tự viết code**, gặp vấn đề cụ thể mới hỏi AI

**Lợi ích của cách này**:
- Tránh lỗi do AI hallucination
- Bạn hiểu hoàn chỉnh về code
- Maintain về sau dễ hơn

## Mô hình phát triển kết hợp

"Phát triển kết hợp" là chiến lược thực tế: để AI làm phần nó giỏi, bạn bổ sung phần nó làm không tốt.

### Mô hình một: AI làm khung xương, bạn làm chi tiết

```markdown
Vui lòng sinh khung code của [chức năng], bao gồm:
- Cấu trúc file cơ bản
- Signature của các hàm chính (tham số và giá trị trả về)
- Comment chức năng của mỗi hàm

Không cần implement logic cụ thể, tôi tự viết.
```

**Tình huống áp dụng**:
- Bạn quen thuộc logic business, nhưng lười dựng khung
- AI có thể hiểu lầm chi tiết, nhưng khung xương là thông dụng

### Mô hình hai: AI làm bản đầu, bạn review sửa

**Workflow**:
1. Để AI sinh code hoàn chỉnh
2. Bạn review, đánh dấu chỗ có vấn đề
3. Với vấn đề đơn giản, để AI sửa
4. Với vấn đề phức tạp, bạn tự sửa

**Checklist review**:
- [ ] Logic code có đúng không?
- [ ] Trường hợp biên có xử lý không?
- [ ] Thư viện và API tham chiếu có tồn tại không?
- [ ] Có rủi ro bảo mật không?
- [ ] Có phù hợp với quy chuẩn dự án không?

### Mô hình ba: Phân công hợp tác

Chia task theo đặc điểm thành hai loại:

| AI chịu trách nhiệm | Bạn chịu trách nhiệm |
|--------|-------|
| Sinh code CRUD chuẩn | Logic business phức tạp |
| Viết template unit test | Implement thuật toán then chốt |
| Sinh khung UI component | Chi tiết tương tác và animation |
| Viết comment tài liệu | Quyết định thiết kế kiến trúc |

## Khi nào nên tìm kiếm sự trợ giúp bên ngoài

Một số vấn đề thực sự vượt quá phạm vi "Vibe Coding + AI" có thể giải quyết. Nhận diện những tình huống này, kịp thời tìm kiếm sự giúp đỡ, là lựa chọn hiệu quả hơn.

### Tín hiệu nên tìm kiếm sự trợ giúp

- Vấn đề liên quan đến lĩnh vực bạn hoàn toàn không hiểu (như bảo mật, tối ưu performance, DevOps)
- Bị kẹt quá 2 tiếng, không có tiến triển gì
- Vấn đề có thể ảnh hưởng đến bảo mật dữ liệu hoặc ổn định hệ thống
- Cần đưa ra quyết định kiến trúc có thể ảnh hưởng lâu dài

### Đi đâu tìm kiếm sự trợ giúp

| Kênh | Vấn đề phù hợp |
|-----|-----------|
| Stack Overflow | Vấn đề chi tiết kỹ thuật, vấn đề đã có câu trả lời chín |
| GitHub Issues | Vấn đề của thư viện hoặc framework cụ thể |
| Forum cộng đồng/Discord | Vấn đề mở cần thảo luận |
| Tư vấn có trả phí/Cố vấn | Vấn đề kiến trúc phức tạp, vấn đề bảo mật |

### Cách đặt câu hỏi hiệu quả

Dù hỏi AI hay hỏi người, câu hỏi tốt có thể nâng cao đáng kể xác suất nhận được sự giúp đỡ:

```markdown
**Tôi muốn làm gì**: [Mô tả mục tiêu bằng một câu]

**Vấn đề tôi gặp phải**: [Mô tả vấn đề cụ thể]

**Tôi đã thử qua**:
1. [Phương pháp đã thử 1]
2. [Phương pháp đã thử 2]

**Code liên quan/Thông tin lỗi**:
[Đính kèm code có thể reproduce tối thiểu hoặc thông báo lỗi đầy đủ]

**Môi trường của tôi**: [Thông tin version tech stack v.v.]
```

## Tóm tắt phần này

✓ **Nhận biết ranh giới**: Cấu hình môi trường, xác minh thời gian thực, logic đặc thù dự án, thao tác bảo mật là điểm yếu của AI

✓ **Ba phương án dự phòng**: Đổi công cụ AI, tìm giải pháp có sẵn, dùng AI học nguyên lý rồi tự implement

✓ **Phát triển kết hợp**: AI làm khung/bản đầu, bạn bổ sung chi tiết và review

✓ **Tìm kiếm sự trợ giúp**: Kẹt quá 2 tiếng, liên quan đến bảo mật kiến trúc thì kịp thời tìm sự trợ giúp bên ngoài

Phòng bệnh hơn chữa bệnh. Phần tiếp theo chúng ta sẽ xem làm sao để từ đầu giảm xác suất AI "không nghe lời".
