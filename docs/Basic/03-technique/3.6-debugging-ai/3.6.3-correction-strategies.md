# 3.6.3 Chiến lược sửa lỗi: Làm sao để AI sửa đúng

## Sau khi học xong phần này, bạn sẽ nắm được

- 4 chiến lược sửa lỗi và tình huống áp dụng
- Quy trình làm việc của "phát triển dựa trên lỗi"
- Nhận diện tín hiệu "vòng xoáy chết" và cắt lỗ kịp thời
- Có một bộ template Prompt sửa lỗi có thể dùng trực tiếp

## Bốn chiến lược sửa lỗi

Trong phần 3.5.3, chúng ta đã học cách đưa feedback hiệu quả cho AI. Phần này tập trung vào chiến lược sửa lỗi **sau khi vấn đề đã xảy ra** - khi code AI cho có vấn đề, làm sao hướng dẫn nó sửa đúng.

| Chiến lược | Tình huống áp dụng | Tư tưởng cốt lõi |
|-----|---------|---------|
| Chỉ ra chính xác vấn đề | Bạn biết cụ thể chỗ nào sai | Đưa ra vị trí + vấn đề + kỳ vọng |
| Đưa ví dụ đúng | Format hoặc cấu trúc không đúng | Trình bày "hình dạng" đúng |
| Làm lại từng bước | Task quá phức tạp dẫn đến sai | Tách ra rồi hoàn thành từng cái |
| Đổi cách hỏi | Cùng một cách hỏi thất bại nhiều lần | Thay đổi góc độ hoặc cách mô tả |

### Chiến lược một: Chỉ ra chính xác vấn đề

**Tình huống áp dụng**: Bạn có thể định vị được cụ thể là dòng code nào, hàm nào có vấn đề.

**Template Prompt**:

```markdown
Code của bạn tại [vị trí] có vấn đề:

**Vấn đề**: [Mô tả vấn đề cụ thể]

**Hành vi hiện tại**: [Code bây giờ làm gì]

**Hành vi mong đợi**: [Code nên làm gì]

Vui lòng sửa vấn đề này, các phần khác giữ nguyên.
```

**Ví dụ**:

```markdown
Code của bạn tại hàm handleSubmit dòng 15 có vấn đề:

**Vấn đề**: Sử dụng localStorage, nhưng đây là dự án server-side rendering

**Hành vi hiện tại**: Gọi trực tiếp localStorage.setItem(), sẽ báo lỗi ở server

**Hành vi mong đợi**: Trước tiên kiểm tra có trong môi trường browser không, hoặc dùng cookies

Vui lòng sửa vấn đề này, các phần khác giữ nguyên.
```

### Chiến lược hai: Đưa ví dụ đúng

**Tình huống áp dụng**: AI hiểu task rồi, nhưng format, cấu trúc output không đúng yêu cầu của bạn.

**Template Prompt**:

```markdown
Format output không đúng.

**Format hiện tại**:
[Trình bày format AI cho]

**Format mong đợi**:
[Trình bày format bạn muốn]

Vui lòng output lại theo format mong đợi.
```

**Ví dụ**:

```markdown
Format trả về của hàm không đúng.

**Format hiện tại**:
Trả về trực tiếp dữ liệu, như `return userData`

**Format mong đợi**:
Format trả về thống nhất `{ success: boolean, data: any, error?: string }`
Khi thành công: `{ success: true, data: userData }`
Khi thất bại: `{ success: false, data: null, error: "Thông báo lỗi" }`

Vui lòng sửa giá trị trả về của tất cả hàm API theo format mong đợi.
```

### Chiến lược ba: Làm lại từng bước

**Tình huống áp dụng**: Task quá phức tạp, code AI output một lần có nhiều vấn đề, sửa vá không bằng làm lại.

**Template Prompt**:

```markdown
Chức năng này chúng ta làm từng bước.

**Bước một (hiện tại)**: [Chức năng cốt lõi tối thiểu]
Chỉ cần implement chức năng này thôi, những cái khác thêm sau.

Sau khi hoàn thành tôi sẽ xác nhận, rồi chúng ta mới làm bước hai.
```

**Ví dụ**:

```markdown
Chức năng xác thực người dùng chúng ta làm từng bước.

**Bước một (hiện tại)**: Chỉ implement đăng ký người dùng
- Form email + mật khẩu
- Validation format cơ bản
- Lưu vào database

Không cần: Đăng nhập, quên mật khẩu, xác thực email, JWT

Sau khi hoàn thành tôi sẽ xác nhận, rồi chúng ta mới làm chức năng đăng nhập.
```

### Chiến lược bốn: Đổi cách hỏi

**Tình huống áp dụng**: Cùng một vấn đề, dùng cùng một cách hỏi hai ba lần, AI vẫn cho câu trả lời sai tương tự.

**Các góc độ chuyển đổi có thể thử**:

| Cách hỏi gốc | Đổi cách hỏi |
|-------|---------|
| Yêu cầu trực tiếp kết quả | Hỏi nguyên lý trước, rồi để AI implement dựa trên nguyên lý |
| Dùng thuật ngữ kỹ thuật | Dùng ngôn ngữ đời thường mô tả nhu cầu |
| Mô tả "muốn cái gì" | Mô tả "giải quyết vấn đề gì" |
| Từ góc độ chức năng | Mô tả tình huống từ góc độ người dùng |

**Ví dụ**:

```markdown
Cách hỏi gốc (thất bại nhiều lần):
"Viết hàm debounce"

Đổi cách hỏi:
"Khi người dùng nhập trong ô tìm kiếm, tôi không muốn mỗi lần gõ một ký tự là trigger một request tìm kiếm,
mà muốn sau khi người dùng ngừng nhập 300ms thì mới gửi request.
Vui lòng giúp tôi implement logic trigger trễ này."
```

## Phát triển dựa trên lỗi: Biến AI thành trợ lý debugging

Khi bạn gặp lỗi, không cần tự phân tích - có thể ném trực tiếp thông tin lỗi cho AI, để nó giúp bạn định vị và sửa.

### Quy trình làm việc

```
Phát hiện lỗi → Copy toàn bộ thông tin lỗi → Cho AI phân tích → Áp dụng sửa chữa → Xác minh → Nếu có lỗi mới thì lặp lại
```

### Template thao tác

```markdown
Khi chạy code gặp lỗi sau:

```
[Paste toàn bộ thông tin lỗi]
```

Code liên quan:
```[ngôn ngữ]
[Paste đoạn code liên quan]
```

Vui lòng phân tích nguyên nhân lỗi và đưa ra phương án sửa.
```

### Ví dụ

```markdown
Khi chạy code gặp lỗi sau:

```
TypeError: Cannot read properties of undefined (reading 'map')
    at UserList (UserList.jsx:12:23)
```

Code liên quan:
```jsx
function UserList({ users }) {
  return (
    <ul>
      {users.map(user => <li key={user.id}>{user.name}</li>)}
    </ul>
  );
}
```

Vui lòng phân tích nguyên nhân lỗi và đưa ra phương án sửa.
```

**AI thường sẽ cho bạn biết**:
- Nguyên nhân lỗi: `users` có thể là `undefined`
- Phương án sửa: Thêm kiểm tra giá trị rỗng hoặc giá trị mặc định

## Cảnh giác với "vòng xoáy chết"

"Vòng xoáy chết" là hiện tượng: bạn yêu cầu AI sửa vấn đề, nó sửa một cái lại tạo ra hai vấn đề mới; bạn lại yêu cầu sửa, vấn đề càng nhiều, code càng rối.

### Nhận diện tín hiệu

- 🚨 Vòng sửa đổi quá 3 lần, vấn đề vẫn chưa giải quyết
- 🚨 Lượng code của AI càng sửa càng nhiều, càng sửa càng phức tạp
- 🚨 Sửa vấn đề A, chức năng B lại hỏng
- 🚨 AI bắt đầu "đi vòng", phương án đưa ra giống với trước đó

### Chiến lược cắt lỗ

Một khi nhận diện được vòng xoáy chết, hãy cắt lỗ quyết đoán:

**Lựa chọn 1: Rollback làm lại**
```markdown
Hướng này đi không thông. Vui lòng quên hết các sửa đổi trước đó, chúng ta bắt đầu lại từ đầu.

[Mô tả lại nhu cầu rõ ràng, có thể cần tách thành task nhỏ hơn]
```

**Lựa chọn 2: Giữ phần dùng được, tự sửa phần còn lại**
```markdown
Vui lòng sắp xếp lại code hiện tại có thể hoạt động bình thường cho tôi,
phần có vấn đề dùng comment đánh dấu ra, tôi tự sửa.
```

**Lựa chọn 3: Đổi công cụ AI thử xem**

Các mô hình AI khác nhau có hiệu suất khác nhau trên các task khác nhau. Nếu một công cụ bị kẹt liên tục, đổi một cái khác thử có thể có bất ngờ.

## Thư viện template Prompt sửa lỗi

### Sửa lỗi runtime

```markdown
Đoạn code này báo lỗi:

Thông tin lỗi:
```
[Thông tin lỗi]
```

Code:
```[ngôn ngữ]
[Code]
```

Vui lòng sửa lỗi này. Nếu cần thêm context, vui lòng cho tôi biết cần thông tin gì.
```

### Sửa lỗi logic

```markdown
Đoạn code này có thể chạy, nhưng kết quả không đúng:

**Input**: [Mô tả input]
**Output mong đợi**: [Mô tả kết quả mong đợi]
**Output thực tế**: [Mô tả kết quả thực tế]

Code:
```[ngôn ngữ]
[Code]
```

Vui lòng tìm vấn đề logic và sửa.
```

### Sửa vấn đề style

```markdown
Style không khớp với kỳ vọng:

**Hiệu ứng mong đợi**: [Mô tả hoặc link screenshot]
**Hiệu ứng thực tế**: [Mô tả vấn đề hiện tại]

Code hiện tại:
```css
[Code style]
```

Vui lòng sửa style để phù hợp với hiệu ứng mong đợi.
```

### Yêu cầu AI tự kiểm tra

```markdown
Vui lòng kiểm tra code trên:

1. Có trường hợp biên nào chưa xử lý?
2. Có chỗ nào có thể gây ra lỗi runtime?
3. Có chỗ nào có thể tối ưu?

Liệt kê vấn đề xong, vui lòng đưa ra code hoàn chỉnh sau khi sửa.
```

## Tóm tắt phần này

✓ **Bốn chiến lược sửa lỗi**: Chỉ ra chính xác → Đưa ví dụ → Làm lại từng bước → Đổi cách hỏi

✓ **Phát triển dựa trên lỗi**: Ném trực tiếp thông tin lỗi cho AI, để nó giúp bạn định vị và sửa

✓ **Cảnh giác vòng xoáy chết**: Sửa quá 3 vòng vẫn chưa xong, hãy cắt lỗ làm lại quyết đoán

✓ **Thư viện template**: Tích lũy các Prompt sửa lỗi thường dùng, nâng cao hiệu suất sửa chữa

Nhưng đôi khi, vấn đề không phải ở cách sửa, mà là AI thực sự không làm được. Phần tiếp theo chúng ta sẽ xem chiến lược dự phòng - khi AI thực sự không làm được thì phải làm sao.
